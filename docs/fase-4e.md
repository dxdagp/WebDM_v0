# Fase 4e: ASER_ZSA, alta de servicios

Lo que definió Dave el 28-nov-2026:

| Decisión | Cómo quedó |
| --- | --- |
| Captura | Partida, **Tipo de servicio**, Descripción, UMB, Grupo de artículos y Estado. En SAP el tipo de material de todo servicio es **ZSA**. Sin Centro y **sin imágenes**. |
| Tipo de servicio | Es **su propio catálogo**, distinto de los Tipos de material (Dave lo decidió el 28-nov-2026). ADMIN lo administra en **Administración → Tipos de servicio**, y cada tipo tiene su **UMB predeterminada**. Es obligatorio para enviar. Si solo hay un tipo activo, los renglones nuevos ya lo traen. |
| UMB | **Depende del tipo**: se propone la UMB predeterminada del tipo elegido. ADMIN la define en **Administración → Tipos de servicio**. Al cambiar el tipo, la UMB cambia a la del tipo nuevo, salvo que el usuario ya haya elegido otra a mano. Si la UMB se deja vacía, se guarda la del tipo. |
| Reglas | Las mismas del alta de materiales: descripción en mayúsculas y sin acentos (la Ñ se queda), máximo 40, y catálogos activos. |
| Duplicados | Contra el **catálogo de servicios**. La misma descripción **bloquea**; una parecida solo **avisa**. |
| Quién la atiende | Cualquier VAL_MAT o DM, porque los servicios no tienen Centro. |
| DM | Escribe el **Código SAP** en su bandeja, como en las altas de materiales, y puede **exportar `Alta_Ser.txt`** con Código SAP, Descripción, UMB y Grupo de artículos. |
| Al terminar | El servicio entra al **catálogo de servicios**, con origen WEBDM y el folio. |

## 1. Probarlo en tu máquina (Windows)

```powershell
cd C:\proyectos\WebDM_v0
.\.venv\Scripts\Activate.ps1
git fetch origin
git checkout fase-4e
git pull
python manage.py migrate      # catálogo Tipos de servicio; UMB y tipo en cada servicio
python manage.py datos_demo   # opcional: tipos de EJEMPLO MO (UMB H) y SE (UMB SER)
python manage.py test
python manage.py runserver
```

1. Como **admin**, abre **Administración → Tipos de servicio** y da de alta tus tipos, cada uno con su **UMB predeterminada** (o usa los de ejemplo de `datos_demo`).
2. Entra como `validador`. En el menú, **Servicios → Crear servicios** ya está activo.
3. Elige MO en un renglón: la UMB cambia a H. Cámbialo a SE: la UMB cambia a SER. Elige a mano otra UMB y vuelve a cambiar el tipo: tu UMB se respeta.
4. Pega desde Excel `Tipo ⇥ Descripción ⇥ UMB ⇥ Grupo de artículos`. Si dejas la UMB vacía, se queda la del tipo.
5. Presiona **Enter**: valida y guarda el borrador. Prueba la descripción de un servicio que ya existe: sale en rojo "Ya existe el servicio … con esta descripción".
6. **Enviar.** Como eres validador, va directo a DM.
7. Entra como `dm`. En **Pendientes → Datos Maestros**, escribe el Código SAP en el renglón, márcalo y usa **Exportar TXT**: sale `Alta_Ser.txt` con ese código.
8. **Terminar altas con el código capturado.** El servicio aparece en **Consulta → Catálogo de servicios**.

Después Dave decidió que el tipo de servicio es **otro catálogo**. Las migraciones `catalogos/0003` y `solicitudes/0006` hacen el cambio (la 0005 había puesto el tipo apuntando a Tipos de material; se deja porque ya estaba publicada):

```sql
-- catalogos 0003: la UMB predeterminada se mueve de Tipos de material al catálogo nuevo
ALTER TABLE "catalogos_tipomaterial" DROP COLUMN "umb_predeterminada_id" CASCADE;
CREATE TABLE "catalogos_tiposervicio" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "codigo" varchar(20) NOT NULL UNIQUE, "descripcion" varchar(100) NOT NULL, "activo" boolean NOT NULL,
    "umb_predeterminada_id" bigint NULL REFERENCES "catalogos_umb" ("id") DEFERRABLE INITIALLY DEFERRED);

-- solicitudes 0006: cada servicio apunta a su tipo de servicio
ALTER TABLE "solicitudes_detalleservicio" DROP COLUMN "tipo_material_id" CASCADE;
ALTER TABLE "solicitudes_detalleservicio" ADD COLUMN "tipo_servicio_id" bigint NULL
    REFERENCES "catalogos_tiposervicio" ("id") DEFERRABLE INITIALLY DEFERRED;
```

`DetalleServicio` ya existía desde la fase 1, con descripción, grupo de artículos y código SAP. Ahora también tiene UMB y tipo de servicio. Al terminar, el servicio entra al catálogo con tipo de material ZSA. La partida queda con `centro_id` en **NULL**.

## 3. El código

- `solicitudes/alta_servicio.py` reúne las reglas:
  - `umb_de(tipo)` (la UMB predeterminada de un tipo), `umbs_por_tipo()` (la tabla que usa la pantalla) y `tipo_propuesto()` (el único tipo activo, si solo hay uno);
  - el formulario y el formset, con `validar_para_envio()`, que revisa obligatorios y duplicados;
  - `guardar_borrador()`, `enviar()` y `faltantes()`;
  - `texto_txt()`, `error_codigo()` y `terminar()`.
- `duplicados.buscar(..., servicio=True)` busca en el catálogo de servicios. Ahí la misma descripción ya es un duplicado, porque los servicios no tienen No. Parte.
- `flujo.terminar_con_codigos()` ahora termina altas de materiales **y** de servicios. El código de un servicio se valida contra el catálogo de servicios: el mismo código puede existir como material.
- `lotes.exportar()` arma `Alta_Ser.txt` con el código que DM escribió en el renglón, aunque todavía no lo haya guardado.
- `alcance.py`: un alta de servicio la ve cualquier VAL_MAT o DM.
- `static/js/alta_servicio.js` maneja agregar renglones con el tipo y su UMB, el pegado desde Excel y `proponerUmb()`: al cambiar el tipo, cambia la UMB solo si estaba vacía o era la del tipo anterior. La vista le pasa `umbPorTipo`, por ejemplo `{"2": "4", "1": "1"}` (id de tipo → id de UMB).

## 5. Ejercicios en `psql`

```sql
-- Servicios dados de alta desde WebDM
SELECT codigo, descripcion, umb, grupo_articulos, folio_origen FROM catalogo_sap_materialsap
WHERE es_servicio AND origen = 'WEBDM' ORDER BY codigo;

-- La UMB que se propone para cada tipo
SELECT t.codigo, u.codigo AS umb FROM catalogos_tiposervicio t LEFT JOIN catalogos_umb u ON u.id = t.umb_predeterminada_id;

-- Servicios capturados por tipo
SELECT t.codigo AS tipo, count(*) FROM solicitudes_detalleservicio d
LEFT JOIN catalogos_tiposervicio t ON t.id = d.tipo_servicio_id GROUP BY t.codigo;
```
