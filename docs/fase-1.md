## 3. De un modelo de Python a una tabla de PostgreSQL

Un **modelo** es una clase de Python que describe una tabla. Ejemplo real, `catalogos/models.py`:

```python
class Centro(models.Model):
    codigo = models.CharField("código", max_length=4, unique=True)
    nombre = models.CharField(max_length=100)
    centro_beneficio = models.CharField("Centro Beneficio (CeBe)", max_length=20)
    activo = models.BooleanField(default=True)
```

Cada atributo es una columna. `CharField(max_length=4)` es `varchar(4)` en PostgreSQL; `unique=True` es una restricción `UNIQUE`; `BooleanField` es `boolean`. Django agrega solo una columna `id` como llave primaria.

El camino completo tiene dos comandos:

1. `python manage.py makemigrations` compara tus modelos con las migraciones existentes y escribe un archivo nuevo en `<app>/migrations/` que describe el cambio. **No toca la base.**
2. `python manage.py migrate` ejecuta en PostgreSQL las migraciones pendientes y anota en la tabla `django_migrations` cuáles ya corrió.

### Ver el SQL que Django genera

```bash
python manage.py sqlmigrate catalogos 0001
```

`sqlmigrate` muestra el SQL **sin ejecutarlo**. Un fragmento real de la tabla de almacenes:

```sql
CREATE TABLE "catalogos_almacen" (
  "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  "codigo" varchar(20) NOT NULL,
  "descripcion" varchar(100) NOT NULL,
  "predeterminado" boolean NOT NULL,
  "activo" boolean NOT NULL,
  "centro_id" bigint NOT NULL,
  CONSTRAINT "almacen_codigo_unico_por_centro" UNIQUE ("centro_id", "codigo")
);
ALTER TABLE "catalogos_almacen" ADD CONSTRAINT "..._fk_catalogos_centro_id"
  FOREIGN KEY ("centro_id") REFERENCES "catalogos_centro" ("id") DEFERRABLE INITIALLY DEFERRED;
CREATE UNIQUE INDEX "almacen_un_predeterminado_por_centro"
  ON "catalogos_almacen" ("centro_id") WHERE "predeterminado";
```

Léelo así:

- **`GENERATED BY DEFAULT AS IDENTITY`**: PostgreSQL numera el `id` solo (1, 2, 3…).
- **`FOREIGN KEY … REFERENCES catalogos_centro`**: la columna `centro_id` solo puede contener un `id` que exista en la tabla de Centros. Es la "llave foránea" que en Python escribiste como `models.ForeignKey(Centro, …)`.
- **`UNIQUE ("centro_id", "codigo")`**: el mismo código de almacén no se repite dentro de un Centro, aunque sí puede existir en otro Centro.
- **`CREATE UNIQUE INDEX … WHERE "predeterminado"`**: un **índice único parcial**. Solo cuenta las filas con `predeterminado = TRUE`. Resultado: un Centro puede tener muchos almacenes, pero nunca dos predeterminados. Esta es la regla "como máximo uno predeterminado" de tu Revisión 3, sección 13, garantizada por PostgreSQL.

En Python esa regla se escribe así (`catalogos/models.py`, función `reglas_por_centro`):

```python
models.UniqueConstraint(fields=["centro"], condition=Q(predeterminado=True), name="almacen_un_predeterminado_por_centro")
```

`Q(predeterminado=True)` es la condición; Django la traduce al `WHERE` del índice.

## 4. ¿Qué protege PostgreSQL y qué protege Django?

Regla práctica: **PostgreSQL protege lo que nunca debe romperse, pase lo que pase. Django protege lo que depende del momento o del flujo.**

| Regla | Quién la protege | Cómo |
| --- | --- | --- |
| Folio único | PostgreSQL | `UNIQUE` en `solicitudes_solicitud.folio` |
| Código SAP de 6 dígitos | Ambos | `CHECK (codigo ~ '^\d{6}$')` + validador con mensaje amigable |
| Código SAP + Centro no se repite | PostgreSQL | `UNIQUE (material_id, centro_id)` |
| Número de partida único en su solicitud, y mayor que cero | PostgreSQL | `UNIQUE (solicitud_id, numero)` y `CHECK (numero > 0)` |
| Máximo 3 imágenes por partida | PostgreSQL | `CHECK (orden BETWEEN 1 AND 3)` + `UNIQUE (partida_id, orden)` |
| Un predeterminado por Centro | PostgreSQL | índice único parcial |
| No borrar un catálogo usado | PostgreSQL | `on_delete=PROTECT` en las llaves foráneas |
| Campos obligatorios al **Enviar** | Django (fase 3) | Un borrador SÍ puede estar incompleto, así que la base no puede exigirlos |
| Transiciones de estado válidas | Django (fase 3) | Dependen de quién actúa y en qué etapa |

Por eso casi todos los campos de `DetalleAlta` tienen `null=True, blank=True`: la Revisión 3 dice "Guardar borrador admite faltantes". Si la base exigiera la descripción, ni siquiera podrías guardar un borrador a medias.

### Detalle curioso: muchos NULL no chocan con UNIQUE

`Solicitud.folio` es `unique=True, null=True`. Un borrador aún no tiene folio (NULL). En PostgreSQL, `NULL` significa "desconocido", y dos desconocidos no se consideran iguales, así que pueden existir mil borradores sin folio y la restricción `UNIQUE` solo actúa cuando el folio tiene valor. La prueba `test_varios_borradores_sin_folio_conviven` lo demuestra.

## 5. El diseño de solicitudes: una Partida común + un detalle por flujo

```
Solicitud (flujo, folio, solicitante, Centro de origen, estado de cabecera)
  └── Partida (10, 20, 30… estado propio, Centro, última devolución)
        ├── DetalleAlta          (si el flujo es AMAT_ZRA)
        ├── DetalleAmpliacion    (AMPL_ZRA)
        ├── DetalleModificacion  (MOD_ZRA o MOD_ZSA)
        ├── DetalleServicio      (ASER_ZSA)
        ├── ImagenPartida (1 a 3, solo altas)
        └── Evento (bitácora)
```

- Cada detalle usa `OneToOneField(Partida, primary_key=True)`: la llave primaria del detalle **es** el `id` de la partida. Una partida tiene como máximo un detalle de cada tipo, y desde Python llegas con `partida.alta`, `partida.ampliacion`, etc.
- **Por qué así:** la bandeja "Pendientes de mi atención", el job de vencimientos (15/30 días desde `ultima_devolucion`) y la bitácora trabajan con `Partida` sin importar el flujo. Y cada flujo sigue siendo explícito, como pide la Revisión 3, sin un "motor genérico".
- `DetalleModificacion.campo` es una lista cerrada (`TextChoices`) con los 9 datos que se pueden modificar. `CAMPOS_SERVICIO` marca los dos que aplican a servicios; la fase 3 lo usará para validar.

`Flujo` es una lista cerrada con los cinco flujos. Su valor (`AMAT_ZRA`, `AMPL_ZRA`, `MOD_ZRA`, `ASER_ZSA`, `MOD_ZSA`) será también el prefijo del folio en la fase 2.

## 6. Usuarios, roles y sesión

- **Roles = grupos de Django.** La migración `usuarios/migrations/0003_roles_iniciales.py` es una **migración de datos**: en vez de crear tablas, inserta los grupos SOL_MAT, VAL_MAT, DM y ADMIN. Así toda base nueva nace con los roles. Fíjate en que trae dos funciones: `crear_roles` (ir hacia adelante) y `borrar_roles` (revertir).
- **Centros autorizados:** `Usuario.centros` es un `ManyToManyField`. En PostgreSQL eso crea una tabla intermedia `usuarios_usuario_centros` con dos columnas (`usuario_id`, `centro_id`): un usuario tiene muchos Centros y un Centro tiene muchos usuarios.
- **Se quitó el campo `area`** de la fase 0; lo reemplazan los Centros.
- **Sesión de 30 minutos sin actividad** (`config/settings.py`): `SESSION_COOKIE_AGE = 1800` y `SESSION_SAVE_EVERY_REQUEST = True`. La segunda reinicia el reloj en cada clic, así que solo expira si el usuario se queda quieto 30 minutos.
- **Contraseña mínima de 8 caracteres:** `MinimumLengthValidator` con `min_length: 8`. Django guarda solo el **hash** de la contraseña, nunca el texto.
- `BitacoraSesion` ya existe como tabla; el código que la llena al entrar y salir llega en la fase 3.

## 8. Practica en `psql`

Abre la consola con el usuario de WebDM:

```bash
psql -h localhost -U webdm webdm
```

Primero da de alta un Centro con dos almacenes en el panel de administración. Luego prueba:

```sql
-- Lista las tablas de WebDM (\dt es un comando de psql, no SQL)
\dt catalogos_*

-- Describe una tabla: columnas, índices y restricciones
\d catalogos_almacen

-- Almacenes por Centro, marcando el predeterminado
SELECT c.codigo AS centro, a.codigo AS almacen, a.predeterminado
FROM catalogos_almacen a
JOIN catalogos_centro c ON c.id = a.centro_id
ORDER BY c.codigo, a.codigo;

-- Intenta romper la regla: debe fallar con
-- "duplicate key value violates unique constraint almacen_un_predeterminado_por_centro"
UPDATE catalogos_almacen SET predeterminado = TRUE;

-- Los roles que creó la migración de datos
SELECT id, name FROM auth_group ORDER BY name;

-- Qué migraciones ya se aplicaron
SELECT app, name, applied FROM django_migrations ORDER BY applied DESC LIMIT 10;
```

`JOIN … ON c.id = a.centro_id` une cada almacén con su Centro siguiendo la llave foránea. Es exactamente lo que hace Django cuando escribes `almacen.centro.codigo`.
